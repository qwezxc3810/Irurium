# 모바일 성능 검증

어항 화면이 휴대폰에서 부드럽게 도는지 재는 도구예요. **개발·검증 환경에서만** 보여요.

| 어디서 | 어떻게 열기 |
|---|---|
| 검증실 | `lab.html#perf` 또는 검증실 "성능 측정" 탭. 장면 3개(어린왕자 14일 · 꾸준형 100일 · 꾸준형 200일) |
| 앱 화면 | 개발 서버(`npm run dev`)이거나 주소 끝에 `?perf=1`. 지금 어항(데모)을 그대로 재요. 일반 주소에서는 패널이 없어요 |

## 보여 주는 값
| 값 | 뜻 |
|---|---|
| **어항 FPS** (1차 지표) | PixiJS가 어항을 **실제로 그린 프레임** 수. 렌더러 ticker에서 그리기(LOW 우선순위)가 끝난 뒤 UTILITY 우선순위로 시각을 기록해요. 패널은 최근 2초, 측정 결과는 측정 구간 전체 |
| 어항 1% 느린 프레임 | 어항 프레임 중 가장 느린 1%의 평균 시간을 FPS로 바꾼 값. 끊김을 봐요 |
| 어항 프레임 지연 | 어항 프레임 시간 평균 · 99% · 최대, 33ms(30fps 아래)를 넘은 프레임 수와 비율 |
| 렌더링 해상도 | 기기 DPR → 실제로 쓴 렌더링 해상도, 캔버스 크기와 실제 픽셀 수 |
| 그리는 생물 | 렌더러가 화면에 그리고 있는 물고기·수초·수석·상징 수(엔진 상태와 같아야 해요) |
| [진단] 브라우저 갱신 간격 | 렌더러와 따로 도는 `requestAnimationFrame` 간격. **어항이 그린 횟수가 아니에요.** 어항이 느리거나 멈춰도 화면 주사율 가까이 나올 수 있어서 성능 판정에 쓰지 않아요. 어항 FPS와 비교해 "어항 쪽이 병목인지" 볼 때만 써요 |
| [진단] 어항 갱신 제한 | 제한 없음 / 30fps / 15fps / 멈춤. 측정기가 어항 FPS를 제대로 잡는지 확인하는 용도. 평소에는 "제한 없음"으로 재고, 제한을 건 결과에는 경고가 붙어요 |

### 측정 방법
- "30초 측정"을 누르면 **2초 준비(워밍업)** 뒤 30초를 재요. 모드를 바꾼 직후의 흔들림을 빼기 위해서예요.
- 측정 구간은 시작~끝 시각으로 정하고, 그 안에서 끝난 프레임만 써요. 결과에는 **실측 시간**과 유효 프레임 시간을 같이 적어요(타이머가 조금 늦게 돌아도 구간 밖 프레임은 들어가지 않음).
- 측정 중에 화면이 숨겨지면(다른 앱, 화면 꺼짐) 숨김 구간을 빼고 결과를 **무효(참고용)**로 표시해요. 1초 넘는 간격도 멈춤으로 보고 버려요.
- 화면이 보이는 동안 어항이 1초 넘게 멈춘 구간이 있으면, 그 간격은 FPS 계산에서 빠져 실제보다 좋게 나올 수 있어서 결과를 **무효(참고용)**로 표시해요.
- 측정 중에 장면·모드·갱신 제한을 바꾸면 그 측정은 취소돼요.
- **성능 판정에는 무효(참고용) 결과와 진단용 갱신 제한을 건 결과를 쓰지 않아요.**
- "측정 기기" 칸에 기종·브라우저·화면 주사율(둘 다 자동 추정해 미리 채움)·절전 모드·화면 밝기·측정 뒤 발열을 적으면 결과 텍스트에 같이 들어가요. 같은 조건끼리만 비교해요. 브라우저·웹뷰 판별은 브라우저 정보로 하는 추정이라, 틀리면 측정자가 고쳐요.

## 일반 모드 vs 저사양 모드
같은 어항에서 버튼으로 바로 바꿔요(어항을 다시 만들지 않음).

| | 일반 | 저사양 |
|---|---|---|
| 렌더링 해상도 | 기기 DPR, 최대 2 | 최대 1 |
| 감정 조명 | 색 보정 필터(ColorMatrixFilter) | 필터 없이 반투명 덧칠 한 장 |
| 왼쪽 위 가산 빛 | 켬 | 끔 |
| 기포(화면 연출) | 최대 24개 | 최대 8개 |
| 빛줄기·별 반짝임 | 켬 | 끔(고정) |

**바꾸지 않는 것:** 생성 엔진, `ENGINE_VERSION`(0.2.0), 스냅샷, 물고기 수, 수초 수, 수석·상징 수, 배치. 품질 설정(`src/render/quality.ts`)에는 화면 연출 항목만 있고, 테스트가 이것과 골든 해시를 확인해요. 계정 설정으로 고정되는 값이 아니고, 측정 비교용이에요.

## 실제 휴대폰 값과 시뮬레이션 값 구분
결과 텍스트 맨 위 **"측정 출처"**로 구분해요.

| 측정 출처 | 조건 |
|---|---|
| ✅ 실제 휴대폰(측정자 확인) | 자동 판정이 휴대폰(휴대폰 브라우저 정보 + 터치)이고, 측정자가 "실제 휴대폰에서 재고 있어요"를 골랐을 때만 |
| ⚠️ 개발 환경 시뮬레이션 | 자동화·헤드리스 브라우저(측정자가 뭘 골라도), 또는 측정자가 "아니에요"를 고름 |
| ⚠️ 미확인 | 휴대폰으로 보이지만 측정자가 고르지 않음. 개발자 도구의 기기 흉내도 휴대폰처럼 보여서 자동 판정만 믿지 않아요 |

## 휴대폰에서 재는 순서
1. 휴대폰으로 검증실을 열고 "성능 측정" 탭으로 가요. 다른 앱은 닫고, 화면 밝기·절전 모드는 평소대로 둬요.
2. 장면을 고르고 일반 모드 → "30초 측정", 끝나면 저사양 모드 → "30초 측정".
3. 장면 3개 모두 반복해요(결과 6개).
4. 결과마다 **렌더링 해상도와 실제 픽셀이 모드에 따라 바뀌었는지** 봐요(예: 일반 DPR 3 → 2, 저사양 → 1). 안 바뀌면 저사양 모드가 그 휴대폰에서 해상도를 못 낮춘 거라 따로 알려 주세요.
5. "측정 기기"에서 **실제 휴대폰에서 재고 있어요**를 고르고 "결과 텍스트 복사". 자동 복사가 막히면 글상자를 길게 눌러 복사해요.
6. 기기 이름(예: 갤럭시 A15)도 함께 보내 주세요. 브라우저 정보에는 기종이 정확히 안 나올 수 있어요.

### 갤럭시 Z 폴드7 (2026-11-16) — 어항 FPS 평균 / 1% 느린 프레임

| 장면 | 일반 (렌더링 2, 676×406) | 저사양 (렌더링 1, 338×203) | 생물 (물고기·수초·수석·상징) |
|---|---|---|---|
| 어린왕자 14일 | 120.5 / 87.5 | 120.7 / 91.5 | 3 · 3 · 1 · 2 |
| 꾸준형 100일 | 120.6 / 84.8 | 120.7 / 91.9 | 4 · 6 · 4 · 2 |
| 꾸준형 200일 | 120.7 / 102.6 | 120.7 / 102.7 | 4 · 9 · 5 · 2 |

- 6개 모두 30초 실측, 33ms 넘은 프레임 0개, 최대 프레임 시간 26.5ms. 무효·진단 제한 없음.
- 평균이 화면 주사율(120Hz)에 붙어 있어서 이 기기에서는 렌더링이 병목이 아니에요. 그래서 저사양 모드로 바꿔도 평균은 같고, 해상도만 실제로 반으로 줄었어요.
- **판단 기준(저사양 안드로이드) 판정에는 못 써요.** 최신 플래그십이라서요. 저사양 모드를 기본값으로 할지는 보급형·오래된 안드로이드 측정 뒤에 정해요.
- Claude 앱 웹뷰에서 잰 값이라, 크롬·삼성 인터넷 같은 일반 브라우저와 다를 수 있어요. 이 측정에서 브라우저 칸이 "크롬 157"로 잘못 채워져서, 이제 안드로이드 웹뷰를 따로 알아봐요.

판단 기준(초안, 실측 뒤 확정): 저사양 안드로이드에서 꾸준형 200일 **일반 모드 어항 FPS 평균 50 이상, 어항 1% 느린 프레임 30 이상**. rAF 값으로는 판정하지 않아요. 못 미치면 저사양 모드를 기본값으로 할지 정해요(가설 H8).

## 그래픽 품질 자동 전환 (앱 설정)
앱 설정의 **그래픽 품질: 자동(추천) / 일반 / 저사양**. 기본은 자동이에요. 위의 일반·저사양 모드를 그대로 쓰고, 생성 엔진·스냅샷·생물 수는 바꾸지 않아요(`src/perf/autoQuality.ts`).

| 규칙 | 값(초안, 보급형 실측 뒤 다듬기) |
|---|---|
| 판정 지표 | 어항 FPS(최근 3초), 약 1초마다 |
| 버거움 | 평균 48fps(60의 80%) 아래, 또는 1% 느린 프레임 30fps(60의 50%) 아래, 또는 3초에 프레임 20개 미만 |
| 멈춤 | 렌더러가 준비됐고 화면이 보이는데 어항 프레임이 0개이거나, 프레임이 덮은 시간이 관찰 시간의 절반 미만(1초 넘는 정지는 FPS 통계에서 빠지므로 따로 봄). 버거움과 같이 세요 |
| 판정하지 않음 | 렌더러 로딩 중(시간도 안 셈), 화면 숨김(연속 기록 끊음), 준비·화면 복귀 직후 1초(그 전 프레임은 쓰지 않음) |
| 목표 60fps 고정 | 화면 주사율로 목표를 정하지 않아요. 그리기가 느리면 브라우저 갱신도 같이 느려져 주사율을 낮게 잘못 보고, 버벅이는 기기를 놓치기 때문이에요. 120Hz 기기도 60fps면 충분해요 |
| 내리는 조건 | 시작 2초는 안 봄. 처음 10초 안에는 3번 연속, 그 뒤(발열 등)에는 8번 연속 버거우면 저사양 |
| 올리지 않음 | 쓰는 중에는 저사양 → 일반으로 자동으로 올리지 않아요(왔다 갔다 하지 않게) |
| 기억 | 자동 판정은 기기에 7일 저장. 지나면 다시 일반으로 시험. 설정의 "일반으로 다시 시험하기"로 바로 다시 시험 |
| 사양 추정(보조) | 메모리 2GB 이하 또는 CPU 코어 2개 이하로 보이면 저사양부터 시작. 브라우저가 알려 주는 값이라 부정확하고, 아이폰은 거의 알려 주지 않아요 |
| 직접 선택 | 일반·저사양을 고르면 자동 판정을 하지 않아요. 선택은 기기에 저장 |

- **갤럭시 Z 폴드7 실측(120fps 안팎, 1% 느린 85~103)** 기준으로는 계속 일반 모드예요.
- 성능 패널의 진단용 "멈춤"을 자동 모드에서 누르면 멈춤으로 판정돼 저사양으로 내려가요(3초). 측정할 때는 그래픽 품질을 직접 고르고 재요.
- 60fps 목표·7일 기억·2GB/2코어 추정은 초기 가설이에요. 30Hz로 제한된 화면·절전 모드·앱 웹뷰에서는 맞지 않을 수 있어서, 보급형·구형 실측으로 다듬어요. 사용자가 직접 고른 품질이 늘 우선이에요.
- **개발 환경 확인(⚠️ 시뮬레이션):** GPU 없는 헤드리스 크롬(코어 2개)에서 사양 추정으로 저사양 시작 → "다시 시험하기" → 일반에서 평균 12~14fps → 4초 만에 저사양 전환 → 판정 저장 → 새로 열면 저사양으로 시작하는 것을 확인했어요.
